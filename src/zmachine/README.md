# Z-machine

Runs Infocom story files on Daisy. Ported from
[jzip](https://github.com/borg323/jzip) 2.1 by Mark Howell and John Holder, by
way of [A2Z_Machine](https://github.com/ZContent/A2Z_Machine), which is the
same interpreter carried to an Arduino Cortex-M board. jzip is BSD licensed;
the files original to this port are GPLv3 like the rest of DaisyOS.

Type `ZORK` at the BASIC prompt.

## Why not emulate a Z80 and run the CP/M version?

`ZORK1.COM` is itself a Z-machine interpreter, compiled for CP/M-80. Emulating
a Z80 to run it means carrying a whole second machine to reach the same
virtual machine one layer down, and it costs a 64 KB address space plus a disk
to hold `ZORK1.DAT`. Running the story directly costs 11,941 bytes of RAM and
no storage hardware at all.

## Layout

| | |
|---|---|
| `zm_interpre` `zm_control` `zm_math` `zm_object` `zm_operand` `zm_property` `zm_text` `zm_variable` `zm_input` `zm_screen` | jzip, essentially unmodified |
| `zm_memory` | **replaced.** Flash-resident story, RAM only for dynamic memory |
| `zm_fileio` | **replaced.** Story access, save and restore |
| `zm_osdep` | **replaced.** Errors, random numbers, odds and ends |
| `zm_vt52` | **replaced.** Screen driver, emits VT52 |
| `zm_run` | Starting and stopping a story |
| `zm_machine` | Story picker, the `ZORK` command |
| `zm_host_daisy` | The only file that touches DaisyOS |
| `zm_stories.cpp` | Generated by `tools/mkstory.py`. Zork I, II and III |

`quetzal.cpp` is not ported. Saves stay on the machine, so the portable save
format buys nothing and costs 619 lines.

## Memory

The story divides at header word `0x0E`. Below it is dynamic memory, which the
game writes to; above it is static and high memory, which it only reads.

```
0              0x2E53                              84992
|  dynamic       |          static + high            |
|  RAM, 11,859   |          flash, 73,133            |
```

jzip pages the file through an LRU cache and, so that dictionary lookups do
not evict the executing page, makes its resident area reach all the way to the
base of high memory: 20,023 bytes for Zork I. The SAM3X maps flash into the
address space, so static memory is already one subscript away and none of that
is needed. Only the writable 11,859 bytes are copied into RAM.

Cost of adding this module, measured:

| | static RAM | flash |
|---|---|---|
| DaisyOS alone | 28,080 | 159,272 |
| with the interpreter, no story | 30,848 | 178,888 |
| with Zork I | 30,848 | 263,808 |
| with all three Zork games | 30,848 | 436,984 |

The interpreter costs 19,616 bytes of flash and 2,768 of RAM whatever the
number of stories; the rest is story image. Static RAM does not move when
stories are added, because they stay in flash. While a story is running
another 11,941 bytes are allocated and freed on exit, so peak use is 42,789
of 98,304 and DaisyBASIC's heap is left alone entirely.

Flash is what limits the story count. The three-Zork build leaves 87,304
bytes free, so a fourth Infocom-sized story would not fit.

## The screen

`zm_vt52.cpp` implements jzip's screen interface by emitting VT52 escape
sequences and nothing else. The firmware feeds those to `daisyos/vt52.cpp`,
which renders into the DaisyVideo shadow RAM; the test harness feeds them to a
virtual screen it can assert against. Neither the interpreter nor its screen
driver refers to DaisyOS.

The status line is drawn in reverse video on row 1, with the text window
scrolling beneath it inside a scrolling region.

## Changes to the interpreter

Beyond the replaced files, the jzip sources needed six fixes. All but the last
two are consequences of the smaller resident area.

- **`z_restart` overflowed `datap`.** It reloaded `(h_restart_size/512)+1`
  whole pages, which is 12,288 bytes into an 11,859 byte buffer. Reloads from
  the flash image now.
- **`get_byte` and friends were direct subscripts of `datap`.** Safe upstream
  only because the resident area covers the dictionary. They are now
  bounds-aware inline functions that fall through to flash, which is what
  makes dictionary lookup at 15,137 work. Writes above the boundary are a
  specification violation and are now reported rather than silently absorbed.
- **Raw pointers into `datap`** in `tokenise_line`, `z_sread_aread` and
  `z_encode` are taken from story-supplied addresses and are now range
  checked.
- **`z_save` and `z_restore` never reported to the story.** In V3 `SAVE` is a
  branch instruction, so the branch data has to be consumed; without that it
  was decoded as the next opcode. This showed up as `failing opcode: 0`
  immediately after a save.
- **The status line assumed 80 columns.** `screen_cols - 31` puts the score
  field at column 9 on a 40 column screen, and because `pad_line` rewinds
  rather than advancing, "North of House" rendered as "North of Score  0".
  Narrow screens get a compact layout.
- **`[MORE]` was never erased.** Upstream relies on the story's next output
  overwriting it; when that output is a newline the prompt scrolls up into
  the transcript.

`fatal()` also unwinds to `ZmRunStory` through `setjmp` rather than spinning
forever, so a malformed story returns the player to the BASIC prompt.

## Testing

`tools/zmtest/` builds the same sources natively and runs them against a
virtual 40x25 VT52 screen, so the interpreter can be exercised without
hardware. The virtual screen implements exactly the sequences
`daisyos/vt52.cpp` does, so anything it cannot render would not have rendered
on the real machine either.

```sh
tools/zmtest/build.sh
tools/zmtest/run-tests.sh /path/to/story/files    # 26 assertions
tools/zmtest/zmtest ZORK1.DAT                     # play it on the terminal
```

Tests assert on what reaches the screen: the banner, room descriptions,
movement, taking objects, the status line layout, save and restore round
trips, `restart`, `[MORE]` paging, all three Zorks, and that a corrupt story
stops cleanly instead of hanging.

## Known gaps

- **Save and restore are unavailable on hardware.** `ZmHostSaveOpen` returns
  NULL and the story is told the save failed. The only writable storage is
  DaisyFile over the WiFi modem, and while `FPRINT` carries 255 bytes a frame,
  reading is one byte per round trip: restoring 13,907 bytes would take
  minutes. Enabling this means adding a block read to the DaisyFile protocol,
  after which only the four `ZmHostSave*` functions in `zm_host_daisy.cpp`
  change. Save and restore are implemented and tested in the harness, which
  uses ordinary files.
- **`terminal.cpp` still has its own copy of the VT52 parser.** The engine in
  `daisyos/vt52.cpp` was extracted from it and is what the Z-machine uses, but
  `TERM` has not been migrated onto it, because that is a change to working
  code that wants testing on real hardware. Doing so would remove the
  duplication and is the obvious next step.
- Accented ZSCII characters are dropped; the DaisyVideo character ROM has no
  glyphs for them.
- V6 graphics and sound are not supported. V1 to V5 and V7 to V8 stories
  should run, though only V3 has been tested.
